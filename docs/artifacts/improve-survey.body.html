Performance

Persist a checksum for system-located binaries so VLC skips its version shell-out

Strong · 92 · performance

internal/tools/detect.go:59 · detect.go:74 · detect.go:145-150 · detect.go:198-213 · internal/tools/defs.go:28

Problem. Detect() loops every known tool including vlc; the manifest entry for a system-located binary never gets a Checksum, so the trust fast path at detect.go:74 can never fire and VLC --version runs on every call.

Solution. In detectOne, compute and persist entry.Checksum in the system-fallback branch (detect.go:198-213) the same way the cache-source branch already does at detect.go:145-150.

  • Measured: VLC --version = 1.97 s
  • powerhour check/doctor/tools list = 2.3–2.4 s
  • This one subprocess is ~85% of that
  • status (never calls Detect) = 0.37 s
  • Reuses the skip yt-dlp already gets

Give a failed update-check the same TTL as a successful one

Strong · 91 · performance

internal/tools/update_check.go:104 · update_check.go:115 · update_check.go:211 · internal/cli/notices.go:33-39 · internal/cli/root.go PersistentPostRun

// update_check.go:115 — a failed entry is never fresh, so it retries every run
fresh := ok && !entry.CheckFailed && time.Since(entry.CheckedAt) < updateCheckTTL
//              ^^^^^^^^^^^^^^^^^^^

Problem. ~/.powerhour/update_check.json currently holds "check_failed": true for ffmpeg. Because !entry.CheckFailed gates freshness, checkHomebrewLatest re-shells brew info --json=v2 ffmpeg on the next invocation, and every one after. printUpdateNotices runs from PersistentPostRun, so this fires for status too.

Solution. In CheckForUpdates, drop !entry.CheckFailed from the fresh condition, or give failed entries a shorter nonzero backoff (1 h) so a persistently-failing brew info is retried on a schedule.

  • Measured: brew info = 0.40 s
  • 0.40 s on every CLI invocation, permanently
  • Failure state is self-sustaining today

Pin publisher checksums for downloaded tool binaries

Strong · 90 · security

internal/tools/releases.go:26-68 · internal/tools/install.go:405-462 · internal/tools/release_dynamic.go:127 · internal/tools/detect.go:74-116

Problem. Every releaseSpec.Checksum in releases.go is hardcoded "", with the comment "populate them as part of the release process when the authoritative SHA256 values are available." ensureDownload skips verification entirely when the checksum is empty. Interface safety

Merge headers inside WriteCSV, matching WriteYAML

Strong · 87 · interface-safety

pkg/csvplan/writer.go:36-42 · writer.go:74-75 · internal/project/collection_mutation.go:118-132 · callers: internal/tui/dashboard/model.go:1152,2766,3016, internal/cli/add.go:73

WriteYAML — self-healing

// writer.go:74
columns = mergeYAMLHeaders(columns, rows)
// new CustomFields always survive

WriteCSV — silently lossy

// writer.go:36
for _, h := range headers {
    if val, ok := row.CustomFields[h]; ok {
        // keys not in headers: dropped
    }
}

Problem. Two functions with the same shape behave oppositely. Any code path that adds a CustomFields key without separately updating coll.Headers loses that data on the next save — no error, no log line — for CSV collections, which is what init generates by default. The YAML branch of the same wrapper is immune to the identical mistake.

Solution. Make WriteCSV's first line headers = MergeHeaders(headers, rows), mirroring WriteYAML. No caller needs to pre-merge.

  • Footgun removed at the API, not at 4 call sites
  • Two write paths behave identically
  • Removes the condition rather than guarding it
